## Phase 1

### Description
<!-- region start: PhaseDescription-->
#### Goal
One build setup in the repository that builds, tests and packs the modules for .NET 10 and .NET 11, so the other phases of this plan only change projects. A developer on the .NET 10 LTS release can use the modules with EF Core 10.

#### What exists today
- 22 module projects target `net11.0`. They are listed in phases 2, 3 and 4. All other module projects target `netstandard2.0`. Every test project and every demo project targets `net11.0`.
- `Directory.Packages.props` holds one version for each package. EF Core, ASP.NET Core, `Microsoft.Extensions.*`, `System.Text.Json`, `Microsoft.Bcl.TimeProvider` and `System.Security.Cryptography.Pkcs` are all `11.0.0`.
- 18 `netstandard2.0` projects reference `Microsoft.Extensions.DependencyInjection.Abstractions`, 10 reference `Microsoft.Extensions.Logging.Abstractions`, and 4 reference `System.Text.Json`. A few more reference `Microsoft.Extensions.Hosting.Abstractions`, `Microsoft.Extensions.Options`, `Microsoft.Extensions.Http`, `Microsoft.Extensions.Configuration.Binder` and `Microsoft.Bcl.TimeProvider`. All are `11.0.0`, so a developer on .NET 10 who installs one of these projects gets the 11.0.0 packages (to check with a test app).
- A trial build on 2026-11-20, in a copy of the repository with every `11.0.0` version set to `10.0.15`, compiled all 58 `netstandard2.0` module projects. No source file in `modules/` has an `#if` on a framework symbol. The trial only compiled, so the run time on .NET 10 is still proved by the tests, see question 3.
- The drivers set a lower bound: `MySqlConnector` 3.0.0 needs `Microsoft.Extensions.Logging.Abstractions` 10.0.15 or higher, and `Microsoft.Data.SqlClient` 7.1.1 needs `System.Text.Json` 10.0.3 or higher. The latest 10.0 release of the `Microsoft.Extensions` packages is 10.0.15.
- `global.json` asks for SDK 10.0.0 and rolls forward to the latest major. The SDK that builds the repository can target `net10.0` (to check).
- `build.cake` builds the `.slnx`, runs `dotnet test` with `NoBuild` on every `*.Tests.csproj` under `tests/` and `demo/`, and packs every project in `modules/`. `dotnet test` runs every target framework of a project that has more than one (to check).
- `.github/workflows/build.yml` installs .NET with `codebeltnet/install-dotnet@v3`. A test run on `net10.0` needs the .NET 10 runtime next to the .NET 11 runtime (to check what v3 installs).
- On `net11.0` the warning NU1510 flags `Microsoft.Extensions.*` references that the framework provides. A project that targets both frameworks may need the reference for `net10.0` only (to check per target framework).
- The namespaces pages are generated by a `Debug` build with DefaultDocumentation. With two target frameworks the generator may run twice (to check).

#### Decided
- **Not in the repo overview.** This plan has no row in the repo overview table of the readme, because it covers all modules and the owner cannot follow it there. It is built first, and the other plans continue after it (owner, 2026-11-20).
- **Support.** The modules support .NET 10 and EF Core 10 next to .NET 11 and EF Core 11 (owner, 2026-11-20). The EF Core 10 release is the LTS release, and the EF Core 11 release is new.
- **Versions in the `netstandard2.0` projects.** They reference the latest `10.0.x` of `Microsoft.Extensions.*`, `System.Text.Json` and `Microsoft.Bcl.TimeProvider`, and not `11.0.0` (owner, 2026-11-20). A .NET 10 developer then gets matching versions, and a .NET 11 developer moves up through the packages of the framework.
- **Multi targeting.** A project that needs more than `netstandard2.0` targets `net10.0;net11.0`, with the package versions per target framework. The `netstandard2.0` projects stay `netstandard2.0` (owner, 2026-11-20).
- **Versions per target framework.** Conditional `PackageVersion` items in `Directory.Packages.props`, one `ItemGroup` with a `Condition` on `$(TargetFramework)` for each framework (owner, 2026-11-20). A package that differs between the two frameworks appears twice. Check that restore evaluates the condition per target framework.
- **Tests.** Every `*.Tests.csproj` targets `net10.0;net11.0` (owner, 2026-11-20). The test run takes twice as long, and every machine and the workflow need both runtimes. It proves that the `netstandard2.0` modules run on .NET 10 with the `10.0.x` packages. The integration tests are a separate question, see [Cat.IntegrationTesting.md](Cat.IntegrationTesting.md#phase-1), question 4.
- **Namespaces pages.** Only `net11.0` generates them, with a condition on the documentation step in the project files (owner, 2026-11-20).
- **The demo.** The demo stays on `net11.0` (owner, 2026-11-20).
- **No build on EF Core 10 only.** The EF Core 11 code is tested as well (owner, 2026-11-19).

#### Done when
`dotnet cake --target=Test` builds and tests a project on both target frameworks, the package versions come per target framework from `Directory.Packages.props`, the workflow has both runtimes, and the namespaces pages are generated once. Every test project of a module that has only `netstandard2.0` projects runs on both target frameworks. A test project cannot run on `net10.0` while it references a project that targets `net11.0` only, so the other test projects switch in phases 2, 3 and 4, together with their projects. `CLAUDE.md` and the `cat-internal-create-module` skill state the rule for the target frameworks.

## Phase 2

### Description
<!-- region start: PhaseDescription-->
#### Goal
The projects that use EF Core build and run on EF Core 10 and EF Core 11.

#### What exists today
These 8 projects target `net11.0` and reference `Microsoft.EntityFrameworkCore`, mostly with `Microsoft.EntityFrameworkCore.Relational`:
- `Cat.EFCore.Commands`, `Cat.EFCore.Extensions`, `Cat.EFCore.Extensions.SqlServer` and `Cat.EFCore.Queries`.
- `Cat.EventProcessor.Inbox.EFCore`, `Cat.Messaging.Outbox.EFCore`, `Cat.Sagas.EFCore` and `Cat.Scheduling.EFCore`.

A trial build on 2026-11-20 compiled the 8 projects against the 10.0.15 packages (the target framework stayed `net11.0`, so this is an early signal and no proof). One project failed: `Cat.EFCore.Extensions.SqlServer`. `TemporalModelBuilderExtensions.cs` calls `HasPeriodStart(x => x.ValidFrom)` and `HasPeriodEnd(x => x.ValidUntil)`, and the EF Core 10 packages only accept a property name as a string there (to check). This is the first API that exists only in EF Core 11.

The test projects use `Microsoft.EntityFrameworkCore.Sqlite` at the same version. The module readme of `Cat.EFCore` says that the projects use EF Core 11 and target `net11.0`.

#### Needs
- Phase 1 of this plan, built first.

#### Decided
- **Both versions.** Every project in the list supports EF Core 10 and EF Core 11 (owner, 2026-11-20).
- **First step.** Build the projects for `net10.0` and list what breaks. An API that exists only in EF Core 11 gives a new question in this phase.

#### Done when
All 8 projects build for both target frameworks and their tests pass on both. The module readmes name the supported versions, and `Cat.EFCore` no longer says that it uses EF Core 11 and targets `net11.0` only. `Cat.EFCore.Extensions.PostgreSQL` of [Cat.EFCore.md](Cat.EFCore.md#phase-2) is built on the same setup.

## Phase 3

### Description
<!-- region start: PhaseDescription-->
#### Goal
The projects that use ASP.NET Core build and run on .NET 10 and .NET 11.

#### What exists today
These 8 projects target `net11.0`:
- With `Microsoft.AspNetCore.App`: `Cat.Api.Gateway`, `Cat.Api.Gateway.Verification`, `Cat.EventProcessor.Authorization`, `Cat.EventProcessor.Minimal.Api`, `Cat.Minimal.Api` and `Cat.Users`.
- With a package of ASP.NET Core only: `Cat.ServiceRequests.Minimal.Api` and `Cat.Users.JwtBearer`.

Packages that need a version per target framework: `Microsoft.AspNetCore.Authentication.JwtBearer`, `Microsoft.AspNetCore.JsonPatch.SystemTextJson`, and `Microsoft.IdentityModel.JsonWebTokens` and `Yarp.ReverseProxy` for their own support of `net10.0` (to check).
- The readmes of `Cat.Minimal.Api` and `Cat.ServiceRequests` say that the JSON patch package supports `net11.0` and up, and that the project targets `net11.0` because of it. A 10.0 release of that package exists (to check on nuget.org).
- The readme of `Cat.Api.Client` explains that `(decimal)29.95d` gives `29.949999999999999289457264240` on .NET 11 and `29.95` on .NET 10. The generated client runs in the application of the developer, so the note may need a line about the runtime.

#### Needs
- Phase 1 of this plan, built first.

#### Decided
- **Both versions.** Every project in the list supports .NET 10 and .NET 11 (owner, 2026-11-20).

#### Done when
All 8 projects build for both target frameworks and their tests pass on both. The readmes that name `net11.0` as the only target are corrected.

## Phase 4

### Description
<!-- region start: PhaseDescription-->
#### Goal
The other projects that target `net11.0` today get the right target frameworks.

#### What exists today
These 6 projects target `net11.0`, with no reference to EF Core or ASP.NET Core:
- `Cat.Messaging.AzureServiceBus` and `Cat.EventProcessor.AzureServiceBus`, on `Azure.Messaging.ServiceBus` and `Microsoft.Extensions.Diagnostics.HealthChecks`.
- `Cat.Sql.Cdc` and `Cat.Sql.Cdc.Messaging`, on `Microsoft.Data.SqlClient`, `Microsoft.Extensions.Configuration.Binder` and `Microsoft.Extensions.Diagnostics.HealthChecks`.
- `Cat.UnitTesting.NUnit` and `Cat.UnitTesting.Responses.NUnit`, on `NUnit` 5 and `Microsoft.Extensions.DependencyInjection`.

Whether a project needs more than `netstandard2.0` is not known. Check the target frameworks of each package on nuget.org.

#### Needs
- Phase 1 of this plan, built first.

#### Decided
- **Rule of the repository.** A module project targets `netstandard2.0` as much as possible, and a project that needs more targets `net10.0;net11.0` (`CLAUDE.md` and owner, 2026-11-20). A project from the list goes to `netstandard2.0` when its packages allow it.

#### Done when
Every project in the list targets `netstandard2.0`, or `net10.0;net11.0` with a note in the module readme that says why. The tests pass on both target frameworks.

## Phase 5

### Description
<!-- region start: PhaseDescription-->
#### Goal
The readmes say which target frameworks and which EF Core versions the modules support, so a developer sees it before picking a package.

#### What exists today
- The readme and `README_NUGET.md` say nothing about target frameworks. The Getting Started chapter of the readme has the badges and three lines about modules and dependencies.
- The NuGet table of a module readme has the columns Package, Role, Install and Downloads. The `cat-internal-create-module-readme` skill fills it with the `NuGetRow` template.
- Some module readmes name a target framework in the text, such as `Cat.EFCore`, `Cat.Minimal.Api` and `Cat.ServiceRequests`. Phases 2 and 3 correct them.

#### Needs
- Phases 2, 3 and 4 of this plan, built first, so the text is true.

#### Decided
- **A column per package.** The NuGet table of every module readme gets a column with the target frameworks of the package, as the monikers from the project file, such as `netstandard2.0` or `net10.0, net11.0`. A module can mix targets, so the answer is given per package. The `cat-internal-create-module-readme` skill fills the column from the project files (owner, 2026-11-20).
- **A legend.** A line under the table says that `netstandard2.0` runs on .NET 10 and .NET 11 (owner, 2026-11-20).
- **The readme.** One line with the rule and no statement about a module: a package targets `netstandard2.0` where possible and otherwise `net10.0` and `net11.0`, the column in each module readme shows which, EF Core 10 and 11 are supported, and the demo runs on .NET 11 (owner, 2026-11-20).
- **`README_NUGET.md`.** It stays as it is, because nuget.org lists the target frameworks on every package page (to check).

#### Done when
A developer finds the supported target frameworks and EF Core versions in the readme and at every package, and the skills keep the text true.
